# 绒点 / Dots 后续开发计划

> 调研日期：2026-10-02。状态：规划建议，尚未实施；不是上线承诺或已完成清单。
> 目标：借鉴 OpenAI dots 与 xAI Grok Bot 的公开能力，把绒点从“能执行任务的私人伙伴”推进为“持续跟进、可检查、可控制成本的私人工作伙伴”。
> 范围：单一主人、自托管、Web + Android。保留原创绒绒，不复用第三方品牌、角色、私有素材或客户端代码。

## 1. 调研结论与证据边界

**两者都有公开技术/使用文档、发布公告及功能宣传，也有额度/计量说明。** 最值得借鉴的不是角色外观，而是持续责任、后台任务可见性、技能复用、审批边界和任务结果交付。

本计划同时覆盖“技术文档”和“计数文档”两种可能含义：

- 技术方面：已查阅官方任务、记忆、渠道、计算机、协作、安全与自动化文档。
- 计数方面：已找到用量、额度重置、计费归属说明；已读来源没有给出完整、固定的每档 token 数量或可直接复制的计价公式。不把消息数当作 agent 工作量。
- 如果“计数”指公开用户数量、采用率或市场规模，本次没有取得足以引用的官方统计；不据宣传语估算。
- 已读文档主要说明产品行为和管理边界，不是完整内部架构、开源实现或绒点可直接调用的 dots/Grok Bot 产品 API。API 可用性需另行核实，不能把普通模型 API 当作这些产品的后台接口。
- 下文“官方说明”只代表公开资料的描述，并非本项目已实测竞品。标为“[推断]”的是基于对照的判断；开发设计与验收指标均是本项目的建议。

## 2. 本地基线与差距

以下基线来自当前本地文件的静态核对，不是生产或设备验收。本次仅新增此文档，不修改已有业务代码、测试或运行数据；后续实现前重新确认源码与工作区差异。

| 能力 | 当前事实与本地证据 | 下一步方向 |
| --- | --- | --- |
| 身份与多 Bot | [README](../README.md)；[companions.py](../server/companions.py)：单主人、独立名字/指令/记忆、受限本地模板。 | 保持私有定位；模板不携带聊天、记忆、登录或授权。 |
| 执行与协作 | [app.py](../server/app.py) 的 `send_turn`、`send_group`、`group_tick`：全局只允许一个活跃/待授权对话，2–4 Bot 群聊按序运行。 | 先建立任务归属和交接，再考虑受限并行；不能仅删除全局锁。 |
| 任务可见性 | [store.py](../server/store.py) 有 conversations/events/approvals/group_queue；[protocol.ts](../src/protocol.ts) 有事件与审批协议。 | 建立跨对话的运行记录、结果与失败摘要；目前没有独立 run/artifact 账本。 |
| 例行任务 | `scheduler`、`next_run`、`/api/routines`；保存 cron/时区/next_run/thread_id/last_error，至少间隔 5 分钟，启动失败后 5 分钟重试。 | 已有 cron，不重复开发“定时器”；补运行历史、漏跑策略、退避、预览与手动试运行。 |
| 技能/工具 | `/api/skills`、`/api/connectors` 列出运行时技能/MCP 状态；[browser_mcp.py](../runtime/browser_mcp.py) 是现有浏览器工具入口。 | 从一次成功任务形成版本化技能，并与例行任务衔接；不另造并行工具链。 |
| 记忆 | `instruction`、`agent_memory`：按 Bot 注入文本记忆，代理保存须主人审批，最多保留 12000 字符。 | 补来源、修改历史、过期/冲突管理；记忆永远不代表新增动作授权。 |
| 浏览器与文件 | [runtime/app.py](../runtime/app.py)、[browser.py](../runtime/browser.py)：持久浏览器、共享单页面引用与锁、工作区路径校验；已有电脑页和文件入口。 | 增加明确的人工/代理控制权，避免接管时代理继续点击；保留 SSRF、egress、工作区限制。 |
| 用量 | `inference` 目前转发上游响应流；Store 没有 usage 专用表。 | 做实际用量归集、未知值提示、预算防护；先核实上游支持，不编造 token/费用。 |
| 移动与渠道 | README、[App.tsx](../src/App.tsx)、[Android](../android/)：Web/Android、语音输入播报、可选后台通知。 | 稳定现有入口后选一个外部渠道；本次未发现 Slack/Teams 适配入口，不将其当作已有能力。 |

[推断] 相较两者，绒点最值得补的是“可靠的持续任务管理”，而不是再加一个 Bot 列表或云电脑页：这些入口已经存在。

## 3. 产品与架构原则

1. **先可靠，再主动，再并行。** 没有运行账本、预算、停止和审批归属，就不开放无人值守并发。
2. **事实与建议分离。** 工具成功、模型说完成、产物生成和主人验收是不同状态；界面展示证据、来源时间和未完成项。
3. **共享资源不是隔离。** Bot 记忆独立，但工作区、浏览器登录属于同一主人；群聊不得自动披露私人对话内容。
4. **确定性权限是底线。** 工具层白名单、网络/路径限制和主人审批先执行；模型审查只能追加限制，不能放宽底线。网页、附件和其他 Bot 输出不能提供授权。
5. **复用现有链路。** 沿用 React 协议/API、FastAPI、SQLite、Codex app-server、MCP 和容器隔离，不更换全部技术栈。随功能增量抽取运行管理、调度、计量模块，避免把所有新逻辑堆进 `app.py`，也不先做大规模重构。
6. **安全迁移。** 新表/列须有版本化迁移与既有数据回归；保留默认绒绒、旧聊天、Bot 和例行任务。升级不清库，旧镜像不等于数据库回滚。
7. **本地/云端分离。** 私有自托管云电脑与主人本机权限分开；不因连接消息渠道而自动获准访问文件或应用。

## 4. 分阶段开发计划

以下月份是顺序参考，不是交付日期；按依赖和验收门槛推进。每阶段必须先交付最小纵向闭环，再扩展场景。所有拟新增能力均未在本次实现。

### M1 / P0：运行账本、活动中心与成本可见性（参考第 1 个月）

**价值：** 先回答“现在在做什么、为何等待、做出了什么、用了多少”。参考 O4/O5/G5/G8。

- 为一次执行建立持久 run 标识，关联 Bot、conversation、turn、父任务、触发来源、时间、状态、审批与产物；事件增量归集，避免重播重复入账。
- 活动中心聚合手动/例行/群聊工作，显示运行中、等待审批、失败、中断、已结束及结果待验收；点击回到真实对话和文件。
- 产物记录保留文件路径、类型、来源 run 和验证说明；“执行已结束”与“目标已验收”分开，不靠模型文本判断成功。
- 在运行时事件或推理转发层归集真实 usage，先核实兼容上游的 JSON/SSE usage 与模型别名映射；流式解析不能缓冲整个响应或破坏原有 SSE。
- 明确运行到上游请求的关联方式；若当前协议没有可靠关联，先补受控标识传递，再提供按 Bot/run 的统计，不能按“当前活跃任务”猜归属。
- 展示输入/输出/缓存等上游实际支持的计量项，模型请求数、工具调用数、耗时单独计数。费用只能依据显式配置的价格与口径估算，标明币种、价格版本及非账单性质。
- 添加日预算、单 run 步数/时长/请求限制和全局暂停后台触发入口。额度未知时显示未知；停止新增模型调用与中止当前执行的效果要分别说明，不能保证已在途调用不收费。

**验收：** 合成运行覆盖成功、待审批、失败、中断；重播同一事件不重复计数；含 usage、缺 usage、SSE 跨块和客户端断开的上游样本均正确处理；预算触顶不启动新的后台 run；列表能定位到真实产物；已有事件渲染/消息回显回归通过。

### M2 / P0：明确控制权、审批范围与停止语义（参考第 2 个月）

**依赖：** M1 的 run/事件关联。参考 O5/G4/G7。

- 每张审批明确主体、工具、目标、参数、风险、有效期限及 run/turn，接受一次只允许该动作；参数、目标或 runtime epoch 改变后重新审批。
- 主人规则从小范围开始：默认询问，允许指定只读动作，拒绝指定目标；发送、发布、支付、删文件、隐私上传仍须明确主人决定。不要以自然语言“总是允许”替代工具层规则。
- 云电脑增加人工接管/归还控制权；接管期间代理浏览器操作禁止执行，排队动作归还后重新校验，而不是直接回放。
- 增加“停止当前 run”“停止关联子任务”“暂停后续触发”的清晰操作及结果回执；独立提供紧急停止全部执行并禁用后台触发。停止不宣称撤销已经完成的外部动作。
- 建立脱敏动作审计：拟执行动作、规则命中、审批人、决定和实际结果；登录/验证码不进入聊天、记忆、截图留档或一般动作参数日志。

**验收：** 同一审批重复提交只执行一次；过期、改参、跨任务授权及网页伪造同意均被拒；人工接管时代理不能点击；停止后待执行群成员不启动；运行时重启后的旧审批失效；现有认证、SSRF、路径校验与受限 egress 回归不退化。

### M3 / P1：可信例行任务与可复用技能（参考第 3 个月）

**依赖：** M1/M2。参考 G6/O4。

- 在现有 routines 上补每次运行历史、关联 run、最近结果、失败阶段和下一次执行；区分“启动成功”与“整次运行成功”。
- 创建/编辑前展示时区、未来数次执行时间、截止日期、产物目的地和授权范围；明确忙碌、停机及夏令时下的漏跑策略。默认避免长时间离线后补发大量任务。
- 手动试运行明确提示会真实执行；输入使用隔离样本，外部写入仍走审批；提供通知去重、失败退避、重试上限和最终失败提醒。
- 从一次成功任务生成技能草稿：输入、步骤、验证方法、输出、审批点、失败策略；主人审阅后保存版本，例行任务引用固定版本，升级版本需要重验。
- 调度使用持久化执行标识/领取机制防重复启动；外部副作用无法仅靠本地事务保证恰好一次，必须依赖目标幂等键或重试前人工核对。

**验收：** fake clock 覆盖至少间隔 5 分钟、无效时区、夏令时和离线漏跑；重复 tick/重启不重复启动同一次工作；失败重试不会重复发送；技能升级不偷偷改变已启用任务；最近成功/失败记录均能关联到结果或原因。

### M4 / P1：长期责任、可追溯记忆与受控主动研究（参考第 4 个月）

**依赖：** M1–M3。参考 O1/O4。

- 建立 responsibility/goal 记录：目标、权威来源、截止时间、下一步、待回复事项、唤醒条件、通知规则、结束条件与预算；从一个长期项目开始，不做无限制自主代理。
- 固定 cron、明确事件、任务完成和受控自主 wake 分开处理；自主安排下次检查仍受主人授权、最小间隔、次数与预算限制，结束/暂停目标后不再唤醒。
- 主动研究只允许工具层验证过的只读连接器。不要把普通浏览器“只看一眼”认定为只读：导航和交互也可能产生外部副作用。没有可信只读工具时暂不开放主动研究。
- 研究只产生主人可见建议/私人笔记，不自动发消息、改应用或控制电脑；任何后续执行回到常规审批链路。
- 将记忆升级为可查看/编辑/删除的条目，包含来源、记录时间、适用 Bot/目标与有效性；偏好、决策和任务状态分开，旧文本安全迁移。保留代理写入记忆须审批的现有边界。
- 对过期/冲突记忆提示核对当前来源；默认不写入秘密，不把删除记忆描述为撤回已发送信息。

**验收：** 目标暂停/结束后无新 wake；同一来源事件去重，缺数据/旧数据不当作最新结果；只读研究不能调用写工具；群聊不能自动披露私人记忆；记忆删除、冲突和旧文本迁移均有隔离回归场景。

### M5 / P1：一个外部渠道与一个只读业务连接器（参考第 5 个月）

**依赖：** M2/M4。参考 O6/G4/G6。

- 首轮建议采用 Slack 消息入口 + GitHub issues/PR 只读信息源；这是开发范围选择，不要求主人已有账号，也不要求部署到生产。可用本地合成事件验证。
- 复用现有 MCP 执行链路，新增适配器仅负责认证、身份映射、去重和受控事件投递；令牌保存在服务器秘密存储，不交给模型、前端或导出模板。
- 只允许映射到唯一主人的已绑定身份；群组白名单、事件签名校验、事件 id 去重、订阅撤销和重试退避必须先完成。
- 渠道接入、业务数据访问和持续监控分别授权；加入频道不自动开始监听，聊天权限不等于 GitHub 数据权限。
- 各渠道保留独立可见消息，必要上下文只传到目标任务；跨受众发布显示目的地和内容，必须审批。
- 先实现“新 issue → 调研/复现材料 → 主人审阅”，不自动合并 PR、公开发布或部署。暂不同时铺开 Slack、Teams、QQ、飞书等多端。

**验收：** 未绑定身份不能驱动任务；伪签名、事件重播、撤销连接和私聊到公开频道的泄露场景被拦截；一个事件只产生一个责任明确的 run；通知失败不重做业务动作；断开连接后不再读取或触发。

### M6 / P2：显式任务交接与受限并行（参考第 6 个月，满足门槛再启动）

**依赖：** M1–M5，尤其任务关联、预算与资源控制。参考 G3/G4/G5。

- 先交付串行的“调研 → 编写 → 审查”任务交接：明确单一负责人、输入、产物和验收标准；Bot 输出不能给下一位 Bot 新增授权。
- 再试点两个互不写入共享文件的只读/纯计算子任务并行，限制并发和总预算。每个子任务独立 run/turn/审批归属，父任务汇总来源、失败和产物。
- 并行前消除当前隐含单活跃任务假设：`local_gate`、`agent_memory`、`agent_routine` 的主体选择及 runtime 浏览器审批必须携带可信任务标识，不能继续查询任意活跃对话猜归属。
- 共享浏览器、登录态、文件修改保持资源锁；先不允许多个 Bot 同时控制同一页面，不把不同屏幕或线程称作安全隔离。
- 父任务停止传播到子任务；交接设深度/次数上限，防循环委派；失败显式报告，不由另一个 Bot 冒充完成。

**验收：** 两个真实独立运行时线程能够交付独立结果；同一文件/浏览器冲突被排队；审批不会串到别的 Bot；父任务停止后无新子任务；重启不静默续跑危险动作；一次子任务失败不会导致父任务虚报全部完成。

## 5. 暂缓事项与不做事项

- **示范学习 / Teach a task：P2，M6 之后另排。** 先有可靠技能格式再录制交互；生成的是待审草稿，录制时暂停/遮蔽登录、支付和秘密。默认不上传录屏；必须在安全样本上回放并保留审批点，不执行原始点击日志。
- **实时语音通话、主动来电、iOS/独立桌面客户端：暂缓。** 已有语音输入播报先稳定；实时语音需额外处理回声、打断、后台行为和成本，不作为持续任务的前置条件。
- **公开模板市场：暂缓。** 如以后建设，只发布经审阅的可导出模板，需许可/版本/内容审查；不公开私人记忆、附件、任务或会话。
- **多租户、多人社交、企业 SSO/SCIM、企业独立 agent 身份：不在此计划内。** 不是靠扩展 Bot 表即可获得的安全能力。OpenAI specialist dots 试点和 Grok Enterprise 管理项仅作为远期参考。
- **不复制竞品价格、角色或“全天自动完成一切”的承诺。** 自托管运行依赖服务器、网络、上游、主人授权与站点规则；登录/验证码失败要交给主人，不能绕过。

## 7. 推荐首个开发包

**从 M1 的“运行记录 + 活动中心”纵向闭环开始**，保持单活跃任务和串行群聊：

1. 明确现有事件到 run/turn/Bot 的映射，列出重启、等待审批和失败转换。
2. 以增量迁移持久化运行记录，并接入手动对话、例行任务和群聊成员执行。
3. 增加活动列表、运行详情和产物链接，不伪造实时进度或成功状态。
4. 使用合成事件验证正常结束、重复事件、失败、中断、旧数据迁移及链接回溯。
5. 核实上游 usage 支持后再交付计量与预算；未支持的字段明确显示未知，不阻塞运行记录的独立验收。

首个包通过后才扩大后台责任范围。开发中若发现上游协议、资源隔离或产品定位与本计划前提不符，先修订计划并保留事实证据，不增加无要求的兼容层。
